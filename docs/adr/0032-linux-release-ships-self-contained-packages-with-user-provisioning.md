# Linux 发行采用自包含 deb/rpm 与显式用户初始化

原 Linux 发布决策（ADR 0018）只提供无 root 的脚本安装。受管机器需要包管理器台账与可镜像仓库，离线机器无法在安装时拉取依赖，安装脚本的审阅成本也偏高。因此新增发行包渠道，同时保留脚本渠道。

决策要点：

- 双轨发行：`.deb` 与 `.rpm` 是完整安装路径，`install.sh` 保留为无 root 环境的次选入口。两者独立安装与卸载，不提供自动迁移。
- 发行包自包含：内置受支持的 CPython 运行时与按锁文件冻结的全部依赖，安装与运行不依赖系统 Python、`uv` 或网络。
- 程序安装与用户初始化分离：包管理器只落程序文件；`personal-agent-memory setup` 以用户身份完成状态目录、API 密钥、Codex 插件与用户级 systemd 服务，并保持幂等与冲突检测。包的安装脚本不操作用户态。
- 发布形态为单包资产加可离线导入的仓库元数据；GPG 签名留作后续可叠加项。
- 支持矩阵为 Ubuntu 22.04、Ubuntu 24.04、Rocky 9 / RHEL 9 与当前 Fedora，均需容器内端到端实测。
- Windows 支持不在本次范围，但 `setup` 与 payload 构建须参数化，为后续 MSI 阶段复用。

考虑过的替代方案：

- 只做发行包、废弃脚本：放弃共享机器与禁 root 环境。
- 依赖发行版 Python 的包：Ubuntu 22.04 系统 Python 为 3.10，低于项目要求的 3.11。
- 把 Node.js 与 Codex CLI 打进包：把发行包变成第三方工具的分发者，引入版本漂移与许可证责任。
- 在 `postinst` 中代跑用户初始化：root 环境没有可靠的用户 systemd 总线，SSH 与 CI 会失败。
- 用手工迁移工具接管脚本安装：当前没有真实需求，先以冲突检测拒绝双重安装。

后果：包安装需要 root，与脚本渠道的权限模型不同，文档必须说明。用户初始化存在 Python 与 bash 两份实现，需以统一元数据格式、统一服务模板语义和测试断言防分叉。卸载必须先由用户运行用户初始化清理再移除发行包，否则残留的用户级服务会因程序文件缺失而反复启动失败。内置运行时必须在构建阶段固定版本并校验哈希，否则发行包的可审计性不成立。离线 payload 体积在数百 MB 量级。RHEL 8 因 glibc 下限不确定暂不承诺。

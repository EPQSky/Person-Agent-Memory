# 索引修复使用持久待办队列

## 背景

KV 中的记忆单元是源数据，Milvus 中的向量行与全文行是派生物。两者可能不一致：嵌入服务超时、进程在写完正排后被强杀、段文件损坏，都会让一条记忆被保存却无法召回。

当前实现用一个每十分钟执行一次的全量扫描兜底：遍历全部作用域，逐条比对索引行，缺失就重建。这个方案有三个缺口：

1. 尝试次数只存在进程内存里，重启即清零，永久失败的单元会被无限重试。
2. 扫描成本随库规模增长，与真实损坏数量无关。
3. 写入方无法知道一条刚写完的记忆是否已经可检索。

## 决策

在 `maintenance.sqlite3` 中增加 `index_outbox` 表，把「待重建索引」变成持久状态。

### 表结构

| 字段 | 含义 |
| --- | --- |
| `unit_id` | 主键，记忆单元 id |
| `region_id` | 所属记忆区，用于审计与状态统计 |
| `scope_*` | 完整作用域五元组，避免重建时再查 KV |
| `attempts` | 已尝试次数 |
| `next_attempt_at` | 下次可尝试的单调时钟秒数 |
| `last_error` | 最近一次失败类型 |
| `status` | `pending` 或 `failed` |
| `created_at` / `updated_at` | 时间戳 |

`done` 的行直接删除，不保留。

### 写入路径

正式写入与采集写入在返回前检查该单元的 chunk 跟踪行（`/index/chunks/{unit_id}`，本地主键查询）。缺失即视为未建立向量索引，入队并立即唤醒工作线程。检查不改写写入结果，也不延长显著时延。

### 工作线程

- 每 5 秒取出一批到期条目，上限 16 条。
- 按 `RETRIEVAL_ONLY` 模式重建，只用检索索引构建器，不重复写正排本体。
- 重建后再次探测逻辑 id，通过才删除条目。
- 失败则 `attempts += 1`，按 5 秒起步、倍增至最长 600 秒的指数退避安排下次尝试（5/10/20/40/80 秒）。
- 连续 5 次失败标记为 `failed`，不再自动重试，等待人工或下一次版本升级。

### 兜底扫描

进程启动时执行一次全量扫描，把既有的未索引单元入队。之后每 6 小时扫描一次，用于捕捉绕过写入路径的损坏，例如 Milvus 段丢失。扫描只入队，不直接重建。

扫描是权威判断：仍缺失的 `failed` 条目会被重置为 `pending` 并清零尝试次数。这样一次长时间故障不会让记忆永久放弃修复，同时重试频率被限制在每 6 小时一轮。

### 可观测性

`/api/v1/status` 增加三个字段：

- `vector_index_status`：`ready`（无待办）、`pending`（有待办）、`degraded`（存在 `failed`）。
- `vector_index_pending`：待办条数。
- `vector_index_failed`：放弃条数。

整体 `status` 仍由内核健康决定，单条永久失败不把服务整体标记为 degraded，避免噪声告警。

## 被否决的方案

- **保持全量扫描、只加内存计数**：重启后计数丢失，无法收敛。
- **写入失败即回滚记忆本体**：记忆本体是证据，丢失不可恢复；索引可以重建。
- **只靠启动扫描**：长时间运行期间产生的损坏要等到下次重启才能修复。
- **把待办放进 Milvus**：索引本身不可信时才需要待办，待办必须放在独立的事务存储里。

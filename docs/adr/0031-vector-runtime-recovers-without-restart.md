# 向量运行时在嵌入端点恢复后自动启用

## 背景

进程启动时会探测一次嵌入端点。探测失败就把 `vector_enabled` 置为 false，并用这份配置装配运行时。结果是：

1. 该进程生命周期内不再装配嵌入器，向量检索与向量写入全部关闭。
2. 即使端点几秒后恢复，也要重启进程才能重新启用向量。
3. `/api/v1/status` 只能显示 `not_configured`，无法区分「没有配置」与「暂时不可用」。

这与索引待办队列的定位冲突：待办队列本来就是为「嵌入服务暂时不可用」设计的，但启动瞬间的失败会把整套机制一起关掉。

## 决策

把「运行时是否装配嵌入器」与「嵌入端点当前是否健康」拆成两个独立状态。

| 状态 | 含义 | 影响 |
| --- | --- | --- |
| `vector_capable` | 运行时配置里是否包含嵌入器 | 决定 `_runtime_config` 的组成，只在启动时确定 |
| `vector_enabled` | 最近一次探测是否成功 | 决定检索与索引是否走向量，运行时可变化 |

### 启动探测

| 探测结果 | `vector_capable` | `vector_enabled` | 处理 |
| --- | --- | --- | --- |
| 未配置嵌入端点 | false | false | 保持现状，`not_configured` |
| 端点不可达 | **true** | false | 仍装配嵌入器，检索走关键词回退 |
| 维度不匹配 | false | false | 视为配置错误，需要修正配置并重启 |
| 成功 | true | true | 正常启用向量 |

关键变化是「端点不可达」仍装配嵌入器。这样端点恢复后不需要重建运行时。

### 恢复后如何补齐索引

后台探测线程每隔 `embedding_reprobe_seconds`（默认 60 秒）检查一次。仅当 `vector_capable` 为 true 且 `vector_enabled` 为 false 时才探测：

1. 探测成功：把 `vector_enabled` 置为 true，清空降级原因。
2. 立即执行一次全量扫描，把期间缺失索引的单元写入 `index_outbox`。
3. 唤醒索引修复线程，按既有退避策略补索引。

`POST /api/v1/index-repairs/retry` 在 `vector_capable` 为 true 但 `vector_enabled` 为 false 时，会先同步探测一次，再处理待办。这样人工重试不必等下一个探测周期。

### 状态口径

`/api/v1/status` 的 `vector_index_status`：

- `not_configured`：`vector_capable` 为 false。
- `degraded`：`vector_capable` 为 true，但端点不健康或存在 `failed` 待办。
- `pending`：存在 `pending` 待办。
- `ready`：端点健康且无待办。

`memory_kernel_status` 在端点不健康时仍为 `degraded`，与既有行为一致。

### 并发

不重建运行时。看门狗的写入只涉及三个字段、待办表与唤醒事件，都在既有锁的保护范围内：

- 探测本身在锁外执行，避免阻塞请求。
- 更新状态与唤醒工作线程在同一临界区内完成，避免出现「已启用但没唤醒」。
- 关闭时先置停止事件，再等待线程退出。

## 被否决的方案

- **重建运行时（替换 `_bundle`）**：必须停止所有工作线程并等待在途请求，否则会关闭正在使用的存储；实现复杂，风险高于收益。
- **端点不可用时也始终上报 `ready`**：会掩盖故障，且检索要等超时。
- **只依赖重启**：正是本次要解决的痛点。
- **维度不匹配也自动恢复**：维度是配置错误，探测多少次都不会变；自动重试只会制造噪声。

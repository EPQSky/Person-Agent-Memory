# Linux 无 root 安装与用户级服务

## Problem Statement

Personal Agent Memory 目前虽然可以通过 `uv tool install` 安装 Python 包，也已有覆盖 wheel、Codex 插件、守护进程健康检查和真实 Hook 的原生安装验收，但完整安装仍要求用户理解源码检出、Python 工具安装、Codex marketplace、插件注册、守护进程命令、数据目录和进程管理。普通 Linux 用户无法通过一个稳定入口完成安装，也没有用户级服务负责登录后自动启动、异常后的状态检查和统一日志查看。

现有发布流程同样缺少明确的原地升级和卸载契约。用户重新安装时不能确信平台状态、API 密钥、记忆库与项目绑定会被保留；卸载时也缺少“只移除程序”和“清除平台状态”之间的安全区分。手工操作容易遗漏 Codex 插件或后台进程，并可能误碰作为权威记忆载体的记忆库。

用户需要一个面向受支持 Linux 环境、无需 root 权限的发行级安装流程。该流程必须保留平台的本地优先、安全边界和数据所有权，并让安装、升级、启动、诊断和卸载成为可预测且可验收的完整生命周期。

## Solution

通过 GitHub Release 发布可独立下载审阅的 `install.sh`、`uninstall.sh` 和源码归档。首版支持 Ubuntu 22.04、Ubuntu 24.04，以及具备兼容用户级 systemd 的主流 x86_64 Linux。安装器在普通用户权限下检查运行环境，可在缺少时自动安装 `uv`，再安装 Personal Agent Memory Python 工具和全局 Codex 插件，生成并启用 `systemd --user` 服务，启动记忆守护进程并执行经过认证的健康检查。

默认平台状态目录为 `~/.local/share/personal-agent-memory`，默认记忆库根目录为 `~/memory-libraries`，两者都可以通过安装参数覆盖。默认服务只监听 `127.0.0.1:7331`，继续使用首次启动生成的受保护 API 密钥和现有 Codex 插件认证行为。安装完成后不打开浏览器，而是在终端显示服务状态、Web 地址、API 密钥文件位置和常用管理命令。

重复运行新版安装器即为升级。升级停止用户服务，更新程序与 Codex 插件，保留平台状态、配置和全部记忆库，再重新启动并验证健康状态。卸载器默认只删除程序、插件和用户级 systemd 服务；显式使用 `--purge` 时额外删除平台状态，但任何卸载模式都不得自动删除记忆库。

## User Stories

1. 作为 Ubuntu 22.04 用户，我希望通过一个安装脚本安装平台，以便不必手工拼接 Python、Codex 和服务管理命令。
2. 作为 Ubuntu 24.04 用户，我希望使用同一套安装流程，以便获得明确支持的安装体验。
3. 作为使用兼容 systemd 的主流 x86_64 Linux 用户，我希望安装器先验证环境能力，以便在不受支持的环境中尽早得到明确结果。
4. 作为普通用户，我希望安装过程无需 root 权限，以便平台只影响我的用户环境。
5. 作为谨慎的用户，我希望安装器永远不调用 `sudo`，以便它不会静默修改系统级软件或配置。
6. 作为用户，我希望安装器检查 CPU 架构和操作系统，以便不会在已知不兼容的平台上继续执行。
7. 作为用户，我希望安装器检查用户级 systemd 是否可用，以便安装完成后服务管理能力确实存在。
8. 作为用户，我希望安装器检查受支持的 Python 版本，以便 Python 包及固定依赖可以正常运行。
9. 作为用户，我希望安装器检查 Git，以便记忆版本和旁置 Git 仓库功能可用。
10. 作为 Codex 用户，我希望安装器检查 Node.js，以便 Codex Hooks 可以运行。
11. 作为 Codex 用户，我希望安装器检查 Codex CLI，以便全局插件可以正确注册。
12. 作为缺少 `uv` 的用户，我希望安装器可以自动安装 `uv`，以便无需额外手工准备 Python 工具管理器。
13. 作为缺少其他必需依赖的用户，我希望看到具体依赖和人工安装指引，以便我能自行选择合适的系统安装方式。
14. 作为不允许提权的用户，我希望依赖缺失时安装器退出而不是调用系统包管理器，以便权限边界保持清楚。
15. 作为审慎的用户，我希望先下载并查看安装脚本再运行，以便不需要执行未经审阅的 `curl | sh` 管道。
16. 作为 Release 使用者，我希望安装器和对应源码归档一起发布，以便安装输入与发布版本可以对应。
17. 作为用户，我希望默认状态目录遵循现有用户数据位置，以便配置、数据库、凭据和派生状态集中管理。
18. 作为用户，我希望默认记忆库根目录清晰且容易找到，以便我可以直接检查和备份权威记忆。
19. 作为已有目录规划的用户，我希望覆盖状态目录，以便把平台状态放到我选择的位置。
20. 作为已有目录规划的用户，我希望覆盖记忆库根目录，以便注册现有 Markdown 目录体系。
21. 作为用户，我希望安装器创建尚不存在的默认记忆库根目录，以便首次启动不因缺少目录失败。
22. 作为用户，我希望安装器拒绝无效或不可用的目录配置，以便服务不会以部分损坏的配置启动。
23. 作为用户，我希望安装器安装真实的发行版 Python 工具，以便命令行行为与项目验收的 wheel 一致。
24. 作为 Codex 用户，我希望安装器注册项目的本地 marketplace 和全局插件，以便所有项目都能使用 Hooks 与 MCP。
25. 作为 Codex 用户，我希望插件继续通过默认受保护密钥文件认证，以便不必把 API 密钥复制到各个项目。
26. 作为用户，我希望守护进程只监听本机回环地址，以便安装器不会扩大网络暴露范围。
27. 作为用户，我希望安装器创建用户级 systemd 服务，以便无需保持终端窗口开启。
28. 作为用户，我希望安装完成后服务立即启动，以便可以马上打开管理界面。
29. 作为用户，我希望服务随用户登录自动启动，以便重启或重新登录后平台自动恢复可用。
30. 作为用户，我希望服务配置引用已确认的数据目录，以便命令行安装参数和后台运行行为一致。
31. 作为用户，我希望安装器等待经过认证的健康检查成功，以便“安装成功”代表真实可用而不只是文件复制完成。
32. 作为用户，我希望健康检查失败时获得可操作的诊断和日志命令，以便排查启动问题。
33. 作为用户，我希望安装结束时看到 Web 地址，以便知道从哪里进入管理界面。
34. 作为用户，我希望安装结束时看到 API 密钥文件位置，以便理解本地认证材料存放在哪里。
35. 作为用户，我希望安装结束时看到启动、停止、重启、状态和日志命令，以便能够维护后台服务。
36. 作为桌面环境用户，我希望安装器不擅自打开浏览器，以便安装过程不打断当前工作。
37. 作为已有用户，我希望重新运行相同版本安装器是安全的，以便修复安装时不会破坏数据。
38. 作为已有用户，我希望运行新版安装器完成原地升级，以便不必先卸载平台。
39. 作为升级用户，我希望升级前用户服务被有序停止，以便不会在替换程序或插件时继续写入状态。
40. 作为升级用户，我希望平台状态、API 密钥、注册表、项目绑定、候选记忆和审计记录保持不变，以便升级不会重置平台。
41. 作为升级用户，我希望全部记忆库及其权威记忆保持不变，以便软件升级不会影响用户内容。
42. 作为升级用户，我希望 Codex 插件同步更新到相同发行版本，以便守护进程与客户端适配器保持兼容。
43. 作为升级用户，我希望升级后服务重新启动并通过健康检查，以便升级完成状态可信。
44. 作为遇到升级失败的用户，我希望安装器清楚报告失败阶段并保留用户数据，以便故障不会演变成数据丢失。
45. 作为准备停止使用平台的用户，我希望运行卸载脚本移除 Python 工具，以便用户环境中不再留下可执行程序。
46. 作为准备停止使用平台的 Codex 用户，我希望卸载器移除全局插件，以便后续 Codex 会话不再触发相关 Hooks 或 MCP。
47. 作为卸载用户，我希望卸载器停止、禁用并移除用户级 systemd 服务，以便不再有后台进程或失效服务定义。
48. 作为可能重新安装的用户，我希望普通卸载保留平台状态，以便未来恢复原有配置和审计数据。
49. 作为重视数据所有权的用户，我希望普通卸载保留所有记忆库，以便卸载软件不会删除权威记忆。
50. 作为需要彻底清理平台状态的用户，我希望显式使用 `--purge`，以便删除凭据、数据库、缓存和其他平台状态。
51. 作为使用 `--purge` 的用户，我希望记忆库仍然保留，以便任何清理模式都不会越权删除用户内容。
52. 作为配置了自定义状态目录的用户，我希望卸载器识别同一安装配置，以便不会只清理默认路径或误删其他目录。
53. 作为配置了自定义记忆库根目录的用户，我希望卸载器把它视为不可删除的用户内容，以便自定义路径得到相同保护。
54. 作为维护者，我希望安装器行为可以在隔离用户环境中完整重现，以便发布前验证不会依赖开发者工作站状态。
55. 作为维护者，我希望安装、升级和卸载验收不会修改项目仓库状态或远程配置，以便发布验证没有隐藏副作用。
56. 作为维护者，我希望验收执行真实 wheel、真实 Codex 插件和真实 Hook，以便覆盖最终用户实际使用的集成边界。
57. 作为维护者，我希望在 Ubuntu 22.04 和 24.04 上运行同一验收入口，以便支持声明由可重复证据支撑。
58. 作为维护者，我希望安装器失败分支产生稳定退出码和明确错误，以便用户和自动化可以可靠判断结果。
59. 作为维护者，我希望 `.deb` 延后到脚本生命周期稳定之后，以便首版不同时维护多个尚未验证的安装模型。
60. 作为高级用户，我希望现有 `uv tool install` 手动路径继续受文档支持，以便可以绕过自动安装器进行定制部署。
61. 作为用户，我希望卸载入口随平台安装到稳定的用户级位置，以便无需保留或重新下载 Release 目录就能卸载。
62. 作为已经配置同名 marketplace 的用户，我希望卸载器只移除本次安装拥有的配置，以便不会破坏我原有或共享的 Codex 配置。

## Implementation Decisions

- 安装生命周期由两个用户可执行入口承载：安装与升级共用安装器，卸载与清理共用卸载器。
- 安装器和卸载器使用严格的 shell 错误处理，失败时返回非零状态，并输出失败阶段和下一步诊断方式；不得吞掉影响可用性的错误。
- 首版支持目标为 Ubuntu 22.04、Ubuntu 24.04，以及具备兼容用户级 systemd 的主流 x86_64 Linux。架构或服务管理能力不满足时应在修改安装状态之前拒绝继续。
- 全部安装操作在当前普通用户范围内完成。安装器、卸载器、服务单元和辅助命令均不得调用 `sudo`，不得修改系统级 systemd 单元或系统包管理数据库。
- 必需依赖包括项目当前支持范围内的 Python、Git、Node.js、Codex CLI 和可工作的用户级 systemd。安装器对这些依赖执行版本或能力检查，缺失时提供明确人工安装指引并退出。
- `uv` 是唯一允许安装器自动获取的外部工具。已存在且可用的 `uv` 应复用；自动安装失败不得触发其他提权或系统包管理路径。
- GitHub Release 同时提供可下载审阅的安装器、卸载器和匹配的源码归档。用户文档采用“下载、审阅、执行”的流程，不把 `curl | sh` 作为推荐安装方式。
- 安装器从与自身对应的发行内容安装 Personal Agent Memory，不隐式跟踪开发分支，也不在用户机器上执行 Git pull。
- Python 命令通过 `uv tool` 安装到用户环境。现有手动 `uv tool install` 流程继续保留，并与自动安装器使用相同的 Python 包产物和受支持版本边界。
- 默认平台状态目录为 `~/.local/share/personal-agent-memory`，默认记忆库根目录为 `~/memory-libraries`。安装器为这两个设置提供显式覆盖参数，并对路径进行展开、规范化和可用性检查。
- 安装器必须持久保存服务启动所需的已确认安装配置，使重复安装、升级和卸载可以一致识别自定义目录；保存位置属于用户级安装元数据，不属于记忆库。
- 卸载器随安装持久化到稳定的用户级位置，安装摘要和发布文档显示其调用方式。用户不需要保留源码归档或 Release 下载目录才能执行普通卸载或 `--purge`。
- 默认服务地址保持为 `127.0.0.1:7331`。安装流程不得放宽现有仅回环监听的安全约束。
- 安装器通过 Codex CLI 注册 Personal Agent Memory marketplace 和全局插件。重复安装或升级必须收敛到当前发行版本，不得产生重复 marketplace 或插件记录。安装元数据记录 marketplace 是由安装器创建还是在安装前已经存在；卸载器只移除由本次安装拥有且未被其他受管组件使用的 marketplace 配置，不得删除用户预先存在或共享的 marketplace。
- 插件继续优先使用现有默认 API 密钥文件认证。安装器不得把明文 API 密钥写入项目、systemd 单元、命令历史或终端成功摘要。
- 用户级 systemd 服务直接运行已安装的 Personal Agent Memory 命令，并传入持久化的状态目录和记忆库根目录。服务具有明确的启动、停止、重启、状态和日志查看方式。
- 安装器在写入或更新服务定义后执行用户级 daemon reload，并启用且立即启动服务。成功返回前必须等待受保护 API 密钥可用，并通过现有认证健康端点确认守护进程就绪。
- “随用户登录自动启动”通过启用用户级 systemd 服务实现。本规格不要求安装器启用 systemd linger，也不要求用户未登录时持续运行。
- 安装完成摘要显示服务当前状态、Web 地址、API 密钥文件路径，以及用户级 systemd 的启动、停止、重启、状态和日志命令。安装器不自动启动浏览器或其他 GUI 程序。
- 重复运行相同版本安装器必须具备幂等性。它可以修复缺失的程序、插件或服务定义，但不得重置平台状态、API 密钥、项目绑定或记忆库内容。
- 运行更高版本安装器执行原地升级：先有序停止用户服务，再更新 Python 工具、Codex marketplace/插件和服务定义，保留安装配置与全部数据，最后重新启动并执行认证健康检查。
- 升级失败必须保留平台状态和记忆库，不得以清理数据作为恢复策略。错误输出应说明服务状态和可用于诊断或重试的命令。
- 默认卸载顺序为停止并禁用用户服务、移除服务定义并 reload、移除 Codex 插件、按所有权判断是否移除 marketplace 注册、移除 Python 工具和持久化卸载入口。已经缺失的组件不得使重复卸载产生误导性成功之外的破坏。
- 普通卸载保留平台状态、安装所指向的记忆库根目录和所有已注册记忆库。卸载结果必须明确说明哪些数据被保留及其位置。
- `--purge` 是清除平台状态的唯一显式入口。它在完成普通卸载后删除已记录的平台状态目录和安装元数据，但不得删除默认或自定义记忆库根目录，也不得遍历并删除已注册记忆库。
- 卸载器不得依据路径名称猜测用户内容。无法证明目标属于平台状态时应保留并报告，而不是删除。
- 发布文档同步提供自动安装、手动 `uv tool install`、升级、普通卸载、`--purge`、服务管理、日志查看、备份责任和支持范围说明。
- 现有原生安装验收作为实现先例继续保留或演进；新生命周期验收应复用真实 wheel、真实 Codex 插件、认证健康检查和真实 Hook，而不是为安装器建立一套替代产品路径。
- `.deb` 只在脚本安装、升级和卸载契约稳定后作为后续发行形式；本规格不为未来 `.deb` 预先引入系统级服务或 root 安装假设。

## Testing Decisions

- 测试只断言用户可观察结果、已安装产物、公共服务状态和数据保留边界，不绑定安装器内部函数、命令排列或临时文件名称。
- 主要且最高层测试接缝是一个端到端 Linux 安装器验收入口。它在 systemd 可用的隔离普通用户环境中执行真实安装器、真实发行 wheel、真实 Codex CLI 插件流程、真实用户服务和真实认证健康检查。
- 同一验收入口在 Ubuntu 22.04 和 Ubuntu 24.04 的 x86_64 环境运行，以支撑明确的发行版支持声明。其他兼容 systemd 的发行版属于能力兼容目标，不要求首版建立完整发行版矩阵。
- 默认安装场景验证默认状态目录、默认记忆库根目录、用户服务定义、服务启用和运行状态、Web 地址、API 密钥文件、Codex 插件以及真实 Hook 的可用性。
- 自定义安装场景验证状态目录与记忆库根目录覆盖会持久进入服务配置，并在重复安装、升级和卸载时保持一致。
- 依赖场景验证受支持环境可以继续安装；缺少 Python、Git、Node.js、Codex 或用户级 systemd 时，安装器在产生部分安装前失败，并给出对应依赖的人工处理指引。
- `uv` 场景分别验证复用已有工具与自动安装缺失工具。自动安装测试使用受控发布输入，不依赖未经固定的开发分支内容。
- 权限场景监测完整安装、升级和卸载过程，确认没有调用 `sudo`、系统包管理器或系统级 systemd，也没有写入需要 root 权限的位置。
- 首次启动场景确认服务只监听回环地址，生成受保护 API 密钥，并通过认证健康检查后才报告安装成功。
- 输出场景断言安装完成摘要包含服务状态、Web 地址、密钥文件位置以及启动、停止、重启、状态和日志命令，同时不泄露 API 密钥正文，也不启动浏览器。
- 幂等场景再次运行同一发行版本安装器，确认服务、marketplace 和插件记录不重复，平台状态、API 密钥和记忆库内容保持不变。
- 升级场景先通过旧版安装器建立包含可识别平台状态和记忆库内容的安装，再执行新版安装器，确认程序与插件升级、服务恢复健康，而 API 密钥、注册状态、审计数据和权威记忆不变。
- 升级失败场景在更新或启动阶段注入可控失败，确认返回非零状态、输出诊断信息，并且平台状态和全部记忆库仍然存在。
- 普通卸载场景确认 Python 工具、Codex 插件、marketplace 注册和用户服务均被移除，而平台状态、API 密钥文件和记忆库内容保留。
- 卸载入口场景确认用户删除原始 Release 下载目录后仍可执行普通卸载与 `--purge`。
- marketplace 所有权场景分别验证安装器新建的专用 marketplace 可以安全移除，而安装前已经存在或被共享的 marketplace 在卸载后仍然保留。
- `--purge` 场景确认平台状态及安装元数据被删除，但默认和自定义记忆库根目录及其全部内容均保留。
- 重复卸载场景确认已缺失的程序或服务不会导致越界删除，也不会触碰用户内容。
- 仓库隔离场景沿用现有原生安装验收，比较执行前后的工作树和 Git remote，确认安装生命周期没有修改项目仓库或远程配置。
- 安装后的集成场景执行真实 Codex Hook，并验证它可以通过已安装插件连接本地守护进程且保持既有 fail-open 输出契约。
- 只有难以通过端到端环境稳定触发的纯边界分支才增加聚焦测试，例如平台识别、路径参数校验、错误分类或命令缺失。低层测试不得复制端到端生命周期断言。
- 发布前的完成门槛是 Ubuntu 22.04 与 24.04 上的端到端验收全部通过，并且现有 Python 测试、静态检查、类型检查和原生安装相关测试无回归。

## Out of Scope

- Windows、macOS、WSL 专用安装体验或原生桌面安装包。
- ARM、aarch64、32 位架构和非 Linux 平台的支持保证。
- Alpine、无 systemd 环境、容器作为最终用户主运行方式，或其他 init 系统适配。
- 系统级安装、root 服务、systemd linger 自动配置或在用户未登录时保证守护进程运行。
- 自动调用 `apt`、`dnf`、`yum`、`pacman`、`snap` 或其他系统包管理器。
- RPM、AppImage、Snap、Flatpak 及首版 `.deb` 包。
- 自动更新守护进程、后台版本检查、静默升级或降级流程。
- Release 代码签名、操作系统信任链、公钥基础设施或企业软件分发策略。
- 自动打开浏览器、托盘应用、原生 GUI 启动器或桌面快捷方式。
- 删除、迁移、合并或自动备份用户的记忆库。
- 改变记忆守护进程、记忆库注册表、权威记忆、记忆版本、Codex Hooks、MCP 或 Web API 的领域行为。
- 局域网或公网监听、多用户服务、团队安装或共享系统服务。
- 自动配置模型服务、下载本地模型或保存第三方模型凭据。

## Further Notes

- 本规格落实 `ADR 0018` 中已经确认的 Linux 发布边界，并保持“一个记忆守护进程管理全部记忆库”“本地优先 Python 服务与 Web 平台”“MVP 聚焦单用户本地 Linux 与 Codex”等既有架构决定。
- 平台状态与记忆库具有不同的数据所有权：平台状态可以通过用户明确的 `--purge` 删除，记忆库承载权威记忆，任何卸载模式都不得自动删除。
- “主流 systemd Linux”表示安装器按能力检测后可以工作，不等同于首版对所有发行版作出测试支持承诺。首版发布证据以 Ubuntu 22.04 和 Ubuntu 24.04 为准。
- 用户仍需按照发布文档备份平台状态和全部记忆库；安装器的保留语义不能替代备份。
- 本 Spec 是父级规划产物，不带实施状态。后续应使用 `$to-tickets` 按可独立验收的纵向能力拆分实施 Ticket。

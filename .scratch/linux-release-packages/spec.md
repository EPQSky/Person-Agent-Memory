# Linux 发行包与离线分发

## Problem Statement

Personal Agent Memory 目前只有一种发行方式：用户下载并审阅 1744 行 `install.sh`，在普通用户权限下安装 `uv`、建立 Python 工具环境、注册 Codex 插件并写用户级 systemd 服务。这种方式对个人开发者可用，但无法覆盖三类真实场景。

第一，受管机器与企业内网通常要求走发行版包管理器：管理员需要版本的台账、可回滚的升级和可镜像的仓库，而不是在每台机器上执行一个 bash 脚本。第二，目标机器不能访问外网时，现有安装器会尝试拉取 Python 包和 `uv`，安装无法完成。第三，`install.sh` 的体量与职责太多，即使有验收脚本，让用户「先审阅再执行」的成本仍然很高；发行包允许用户在安装前枚举文件、核对校验和，把信任建立在对产物的检查上。

同时，现有安装器把两件事混在一个入口里：把程序文件放到机器上（程序安装），以及把平台连接到具体用户的记忆库、密钥与 Codex 插件（用户初始化）。发行包必须把这两件事拆开，否则系统包管理器会以 root 身份代做用户态动作，在 SSH、CI 等没有用户 systemd 总线的环境里直接失败。

## Solution

发布自包含的 `.deb` 与 `.rpm` 发行包，并通过 GitHub Release 同时提供可离线导入的仓库元数据。发行包内置 Python 运行时与全部依赖，安装过程不需要网络，也不需要 `uv`；安装后由用户执行一次 `personal-agent-memory setup` 完成用户初始化。

Linux 上保留两种安装渠道：发行包是完整路径，`install.sh` 继续作为没有 root 权限环境的次选入口。两者共享同一套用户初始化行为与元数据格式，但各自独立安装、独立卸载；`setup` 检测到双重安装时拒绝继续，不静默覆盖。

支持矩阵为 Ubuntu 22.04、Ubuntu 24.04、Rocky 9 / RHEL 9 与当前 Fedora，四者均需实测通过。Windows 支持不在本规格范围内，但本规格要求用户初始化实现与 payload 构建参数化，为后续 MSI 阶段复用。

## User Stories

1. 作为 Ubuntu 24.04 用户，我希望用 `apt` 从本地文件安装发行包，以便不必审阅并执行一个大脚本。
2. 作为 Fedora 或 RHEL 用户，我希望用 `dnf` 安装同名发行包，以便获得与 Ubuntu 用户一致的平台能力。
3. 作为企业管理员，我希望把 Release 的仓库目录放到内网 HTTP 服务，以便多台机器可以安装、查询版本并升级。
4. 作为离线环境用户，我希望整个安装过程不访问网络，以便在隔离网络中也能完成部署。
5. 作为使用 Ubuntu 22.04（系统 Python 3.10）的用户，我希望发行包自带运行时，以便不需要先升级系统 Python。
6. 作为审慎的安装者，我希望在安装前用 `dpkg -c` 或 `rpm -qlp` 列出包内文件，以便确认内容符合预期后再安装。
7. 作为审慎的安装者，我希望 Release 提供校验和文件，以便核对下载的发行包没有被篡改。
8. 作为安装者，我希望在安装前知道 Node.js 与 Codex CLI 是前置条件，以便缺失时先补齐而不是装完才发现不可用。
9. 作为安装者，我希望在前置依赖缺失时得到具体缺失项和修复指引，以便自行处理。
10. 作为安装者，我希望包安装过程不创建或修改我的记忆库、平台状态与 API 密钥，以便信任边界清楚。
11. 作为安装者，我希望装完包后执行一条命令完成初始化，以便平台连接到我自己的用户环境。
12. 作为用户，我希望初始化后守护进程立即启动并随登录启动，以便不需要保持终端窗口。
13. 作为用户，我希望初始化命令可以重复执行，以便修复配置而不破坏已有数据。
14. 作为用户，我希望初始化命令检测到已有脚本安装或端口占用时拒绝执行，以便不会出现两套程序争抢同一端口。
15. 作为用户，我希望初始化命令检测到 PATH 上存在另一个同名命令时明确报告，以便不会误以为在使用包安装的版本。
16. 作为用户，我希望初始化后能看到服务状态、Web 地址、密钥文件位置和常用管理命令，以便知道接下来做什么。
17. 作为升级用户，我希望用包管理器升级后重跑一次初始化即可刷新服务定义，以便升级路径简单可预期。
18. 作为升级用户，我希望升级不会触碰平台状态、审计记录与记忆库，以便数据在版本变更中保持稳定。
19. 作为卸载用户，我希望移除发行包时程序的系统文件被清理，而我的平台状态与记忆库保留，以便重新安装后能继续使用。
20. 作为需要彻底清理的用户，我希望显式清理平台状态有明确入口，以便区分「移除程序」和「删除数据」。
21. 作为已有脚本安装的用户，我希望继续使用现有安装器和卸载器，并保持既有行为不变，以便本次变更不影响我。
22. 作为用户，我希望发行包版本、插件清单版本与项目版本一致，以便组件之间不会错配。
23. 作为用户，我希望初始化命令在版本不一致时拒绝继续，以便避免半升级状态。
24. 作为维护者，我希望用一条命令构建出 deb 与 rpm，以便发布流程不依赖手工重复操作。
25. 作为维护者，我希望构建不在开发机环境中进行，以便不会把开发机的依赖误带进 payload。
26. 作为维护者，我希望验收脚本在干净容器中安装真实发行包并完成真实记忆读写，以便「能安装」等于「能用」。
27. 作为维护者，我希望四个支持发行版都跑同一套验收，以便发行承诺有证据支撑。
28. 作为维护者，我希望验收脚本使用隔离的 HOME 与 XDG 目录并在结束后清理，以便验收不污染开发机。
29. 作为维护者，我希望构建脚本把运行时来源、安装前缀和服务注册方式参数化，以便后续 Windows 阶段复用同一框架。
30. 作为维护者，我希望发行资产清单与发布文档一致，以便用户不需要猜测该下载哪些文件。
31. 作为维护者，我希望仓库元数据可以由 Release 资产直接生成并离线导入，以便不依赖托管服务。
32. 作为未来 Windows 用户，我希望用户初始化逻辑与平台无关，以便后续 MSI 阶段不需要重新设计初始化语义。

## Implementation Decisions

- 发行渠道改为双轨：发行包是完整安装路径，`install.sh` 保留为次选入口。两种渠道各自独立安装与卸载，不提供自动迁移；本规格不重构 `install.sh`，也不删除其现有能力。
- 新增用户初始化子命令 `personal-agent-memory setup`，承载脚本安装器当前承担的除「程序文件落位」以外的全部用户态动作：前置依赖与版本一致性检查、状态目录与记忆库根目录准备、API 密钥生成与权限设置、Codex 插件注册、用户级 systemd 服务生成与启用、认证健康检查、安装摘要输出。
- `setup` 接受与安装器一致的覆盖参数（状态目录、记忆库根目录、端口、marketplace 采纳开关），并沿用相同的默认值：状态目录位于用户数据目录、记忆库根目录位于用户主目录、服务只监听 `127.0.0.1:7331`。
- `setup` 必须幂等：重复执行收敛到当前状态，修复缺失的服务定义、插件注册与目录，不重置 API 密钥、平台状态、项目绑定或记忆库内容。
- `setup` 必须执行冲突检测后再写任何用户态状态：既有安装元数据、同名命令的 PATH 遮蔽、目标端口占用、以及非本安装拥有的用户级服务定义。冲突按安装方式区分处理：元数据属于同一安装方式时是幂等收敛，不得拒绝；元数据属于另一安装方式时拒绝。其余三类冲突一律以非零状态退出并给出可执行的处理指引，不静默覆盖。
- 安装元数据保留在现有用户级路径，并新增安装方式字段区分 `script` 与 `package`。包安装不写入脚本安装专属的卸载器所有权字段；`setup` 发现 `script` 方式元数据时视为双重安装并拒绝。既有脚本工具读到 `package` 方式元数据时必须安全失败并给出可读提示，不得误删或误改包安装的文件。
- 用户级 systemd 服务由 `setup` 生成到用户级配置目录。服务定义与既有安装器模板保持语义一致：同一目录参数、同一端口、同一重启策略；守护进程命令按渠道使用各自的安装前缀。发行包不提供系统级或全局用户模板单元，避免出现第二套所有权机制。
- 发行包不包含 `postinst`/`postrm` 以外的用户态操作。安装脚本只做文件落位和文档提示，绝不调用 `systemctl --user`、不写用户主目录、不以 root 身份代做初始化。
- 用户态清理由 `setup --uninstall` 承担：停止并禁用用户级服务、移除服务定义、移除智能体插件注册；可选清除平台状态；永不删除记忆库。文档规定卸载顺序为「先运行 `setup --uninstall`，再移除发行包」，因为包卸载后残留的服务定义会因程序文件缺失而反复启动失败。
- 发行包自包含：内置受支持的 CPython 运行时（x86_64 Linux 构建）与按锁文件冻结的全部依赖，安装后无需网络、无需 `uv`、不依赖系统 Python 版本。运行时与依赖的获取只发生在构建阶段。构建阶段固定运行时版本并校验发布方哈希，依赖轮子按锁文件哈希校验；校验失败时构建中止。
- 发行包布局使用独立前缀（`/opt` 下的产品目录）承载运行时、虚拟环境与 Codex 插件；命令行入口通过系统可执行目录中的包装器暴露；文档与许可证进入发行版约定位置。
- 包管理器只拥有程序文件；平台状态、记忆库、API 密钥与用户级服务定义属于用户资产，不进入包的清单，也不由包升级替换。
- 发行包版本、插件清单版本与项目版本必须同源一致。构建阶段校验一致性并拒绝发布不一致的产物；`setup` 在运行期再次校验。
- 构建脚本在固定基础镜像的容器中执行：下载并解包运行时、按锁文件预取多平台兼容的依赖轮子、创建虚拟环境并安装项目、校验导入与版本。构建输出到临时目录，不修改工作树。
- 打包使用一份配置驱动两种包格式，共享同一 payload 与元数据；包名、版本、描述、依赖提示与文件清单集中维护。
- 发布资产至少包含：`.deb`、`.rpm`、校验和文件，以及包含 apt 索引与 RPM 仓库元数据的可离线导入目录。仓库元数据由发布资产生成，不依赖托管服务。
- 验收脚本在干净容器中执行：安装发行包、运行 `setup`、复用现有原生安装验收的认证 HTTP 断言序列（健康检查、内核状态、区域树、项目绑定、记忆写入与召回），并在隔离的 HOME/XDG 环境中运行、结束后清理。
- 验收矩阵为 Ubuntu 22.04、Ubuntu 24.04、Rocky 9 / RHEL 9 与当前 Fedora。未实测的组合不写入支持承诺。
- 文档同步更新支持矩阵、发行资产清单、离线安装与升级步骤、初始化与卸载语义，并在架构决策记录中补充「发行包与离线分发」决策、修订原 Linux 发布决策中「不提供 `.deb`/RPM」的结论。
- 实现须保持与既有架构决定一致：单用户、本机、仅回环监听、单一记忆守护进程、平台状态与记忆库的所有权区分。

## Testing Decisions

- 测试只断言用户可观察行为与产物，不绑定内部函数、临时文件名或命令排列。
- 主要代码层测试缝是命令行行为：以子进程或测试客户端调用 `setup`，在临时 HOME 与 XDG 目录下运行，PATH 前置伪造的 `systemctl`、`codex`、`node`、`git` 命令，断言创建的状态与权限、服务定义内容、插件注册、幂等重跑、四类冲突检测的退出码与诊断信息。先例为现有安装器测试使用伪造命令与临时 HOME 的做法。
- 代码层测试须断言 `setup` 生成的服务定义在目录参数、端口与重启策略上与安装器模板一致，防止两条渠道在服务配置上分叉；守护进程路径按渠道前缀不同，不要求内容一致。
- 主要交付层测试缝是发行包端到端验收脚本：在四个目标容器内安装真实包、执行真实 `setup`、运行真实守护进程并通过认证接口完成记忆写入与召回。先例为现有原生安装验收脚本及其隔离 HOME、健康检查与记忆读写序列。
- 验收脚本必须验证离线约束：安装与初始化过程中不出现对外网络访问，且不依赖 `uv`。
- 验收脚本必须验证数据保留：包卸载后平台状态与记忆库仍存在；显著清理入口只删除平台状态，不删除记忆库。
- 验收脚本必须验证双重安装拒绝：已存在脚本安装时，`setup` 拒绝执行并给出指引。
- 构建脚本、打包配置与仓库索引生成不写单元测试，由端到端验收覆盖。验收脚本允许一条静态约束断言，验证隔离 HOME/XDG、清理逻辑与失败阶段报告，沿用仓库既有的验收脚本测试先例。
- 发布前完成门槛：四个容器的端到端验收全部通过；现有 Python 测试、静态检查与类型检查无回归；既有安装器验收保持通过。

## Out of Scope

- Windows 与 macOS 安装包（含 MSI），以及其平台适配实现。
- GPG 签名、公钥分发与操作系统信任链集成；校验和文件是首版信任手段。
- RHEL 8 及其他 glibc 下限不确定的发行版。
- CI 流水线、自动发布与制品仓库托管。
- 系统级服务、多用户安装、systemd linger 自动配置。
- `install.sh` 的重构、功能删减或改为调用新子命令。
- 自动更新、后台版本检查、静默升级或降级。
- AppImage、Snap、Flatpak 及其他包格式。
- ARM 与其他架构。
- 无 systemd 环境、容器作为最终用户主运行方式。
- 记忆守护进程、记忆库、检索、Codex Hook、MCP 与 Web API 的领域行为变更。
- 自动配置模型服务或保存第三方模型凭据。

## Further Notes

- 本规格扩展先前的「Linux 无 root 安装与用户级服务」规格。先前规格把 `.deb`/RPM 列为范围之外，本规格正式引入发行包渠道，但不改变其已确认的数据所有权、回环监听、单守护进程与升级保留语义。
- 双重实现的风险需要显式管理：发行包渠道引入 Python 实现的用户初始化，而脚本渠道仍保留 bash 实现。缓解手段是统一元数据格式、统一服务模板语义，并用测试断言两条渠道的服务定义一致；长期收敛方向是脚本在安装完 Python 工具后委托 `setup`，这属于后续独立变更。
- glibc 下限取决于所选运行时构建与依赖轮子的标签。实现阶段必须确认所选运行时能在四个目标发行版上运行；若无法满足，应调整运行时版本而不是扩大断言范围。
- 离线 payload 体积预计在数百 MB 量级，用户在离线介质上分发时需要预留空间；文档应说明体积构成与精简方式。
- 发行包安装需要 root 权限，与脚本渠道的「免 sudo」形成明确差异。文档必须直说这一点，避免用户误以为两者权限模型相同。
- 本规格是父级规划产物，不带实施状态。后续应使用 `$to-tickets` 按可独立验收的纵向能力拆分实施 Ticket。

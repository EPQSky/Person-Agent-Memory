# mem2.0 替换本地记忆内核

## Problem Statement

当前项目同时维护两套记忆实现。自研内核负责 Markdown 扫描、分块、混合检索、候选治理、本地 Git 版本和图投影。`JiuwenMemory 0.1.2` 只承担图投影存储。

`JiuwenMemory 0.2.0`（mem2.0）是上游全量重写。公开入口变为 `MemoryAPI` 和统一 Storage。旧的 `jiuwen_memory.foundation.store.graph` 已移除。当前图适配器无法直接升级。

继续维护两套内核会重复实现记忆写入、索引、检索、生命周期和治理。项目仍处于开发阶段，只有单人测试，不需要旧数据迁移。目标是用 mem2.0 替换现有内核，同时保留本地 Codex 集成、管理台和轻量部署。

个人记忆天然分层：用户记忆跨项目，专题记忆对应技能或课程，项目记忆对应具体项目。当前产品没有完整的跨区域召回，智能体无法把用户偏好、专题知识和多个项目经验串联起来回答一个问题。

## Solution

以 `JiuwenMemory 0.2.0` 作为唯一记忆内核。保留现有产品外壳：FastAPI 管理台、API Key、Codex Hooks、MCP、项目绑定和安装器。

新内核使用 SQLite KV 保存记忆单元。Milvus Lite 3.x 同时提供稠密向量索引、BM25 全文索引和图节点/边存储。图遍历在应用层执行。开发测试不把 Docker 作为前置条件。

记忆区域分为用户、专题和项目三类。用户记忆区域映射到 `space=user`；专题记忆区域映射到 `space=topic:<id>`；项目记忆区域映射到 `space=project:<id>`。项目记忆区域是绑定项目根目录的专题区域。记忆区域树用于管理台导航，space 之间是 peer 关系。项目绑定保存项目根目录到项目记忆区域的显式关联。会话采集直接进入内核，由 `evolve` 完成晋升和巩固。不保留独立候选审核层。管理台通过 `inspect`、`update`、`delete`、`audit` 后台更正错误记忆。Markdown 只作为可选导出视图。

检索默认只查当前项目区域。全局召回显式选择用户区域和一个或多个专题或项目区域，结果按来源区域分组，并受预算上限约束。

非项目会话写入会话记忆区域。自动晋升是多目标的：会话、项目和专题记忆都可以晋升到用户记忆或专题记忆；项目特定内容留在项目记忆；临时内容留在会话记忆或按保留策略清理。

迁移采用全新状态目录，不导入旧数据，不保证旧状态兼容。开发阶段允许清空并重建。

## User Stories

1. 作为项目维护者，我希望 mem2.0 成为唯一记忆内核，以便不再维护两套记忆实现。
2. 作为项目维护者，我希望旧自研内核退出主路径，以便写入、检索和治理只有一条代码路径。
3. 作为开发者，我希望使用全新状态目录，以便不被旧数据格式和历史状态干扰。
4. 作为开发者，我希望可以清空测试状态，以便快速重复验证。
5. 作为开发者，我希望不依赖 Docker，以便本地启动保持轻量。
6. 作为开发者，我希望使用 SQLite KV 保存记忆单元，以便重启后数据仍然存在。
7. 作为开发者，我希望使用 Milvus Lite 保存稠密向量，以便本地获得语义召回。
8. 作为开发者，我希望使用 Milvus Lite 保存 BM25 全文索引，以便精确召回标识符、路径和错误码。
9. 作为开发者，我希望向量和全文共用一个本地 Milvus Lite 数据目录，以便减少存储引擎数量。
10. 作为中文用户，我希望全文索引使用 Jieba 分析器，以便中文记忆可以被正确分词和召回。
11. 作为 Codex 用户，我希望项目记忆区域映射到独立 space，以便不同项目默认不互相污染。
12. 作为 Codex 用户，我希望用户记忆区域映射到独立 space，以便跨项目个人信息可以单独管理。
13. 作为 Codex 用户，我希望项目绑定解析为稳定的项目记忆区域，以便 Hook 和 MCP 始终读写正确的记忆边界。
14. 作为 Codex 用户，我希望 worktree 可以显式继承主项目的绑定，以便相关工作树共享记忆而不依赖目录名猜测。
15. 作为 Codex 用户，我希望会话采集直接写入记忆内核，以便用户消息和助手最终回复可以沉淀。
16. 作为 Codex 用户，我希望 `evolve` 负责晋升和巩固，以便工作记忆可以转为长期记忆。
17. 作为 Codex 用户，我希望采集不经过独立人工审核队列，以便记忆沉淀不被审批流程阻塞。
18. 作为 Codex 用户，我希望检索结果不超过 10K tokens，以便上下文预算保持可控。
19. 作为 Codex 用户，我希望检索同时使用全文和向量，以便关键词精确匹配和语义相似召回都能工作。
20. 作为 Codex 用户，我希望检索支持图扩展，以便发现与查询实体相关的记忆。
21. 作为 Codex 用户，我希望图节点对应真实记忆单元，以便图扩展结果保留来源引用。
22. 作为 Codex 用户，我希望图扩展默认一跳，以便联想范围有界。
23. 作为 Codex 用户，我希望图、向量、全文或模型失败时仍能返回可用结果，以便 Codex 主流程不被阻塞。
24. 作为 Codex 用户，我希望 MCP 检索契约保持稳定，以便现有插件不需要重写交互方式。
25. 作为 Codex 用户，我希望 MCP 健康检查能报告内核状态，以便快速判断记忆服务是否可用。
26. 作为用户，我希望在管理台查看记忆单元的完整内容，以便确认记忆是否正确。
27. 作为用户，我希望查看记忆单元的旧版本和生命周期状态，以便理解一次更正的上下文。
28. 作为用户，我希望使用 `SUPERSEDE` 更正记忆，以便旧内容被保留并可追溯。
29. 作为用户，我希望使用 `OVERWRITE` 做小范围修正，以便避免不必要的版本链增长。
30. 作为用户，我希望使用 `FORGET` 遗忘错误记忆，以便错误内容不再参与默认召回。
31. 作为用户，我希望使用 `ARCHIVE` 归档低频记忆，以便保留内容但降低干扰。
32. 作为用户，我希望使用 `DOWNWEIGHT` 降低记忆权重，以便保留内容但减少优先级。
33. 作为用户，我希望使用 `PURGE` 做彻底删除，以便在需要时移除真源和派生索引。
34. 作为用户，我希望查看审计记录，以便知道谁在什么时间修改了哪条记忆。
35. 作为用户，我希望沿 `provenance` 追溯记忆来源，以便判断一条记忆来自哪次会话或哪份内容。
36. 作为用户，我希望用旧内容恢复被替换的记忆，以便纠正误改而不重写历史。
37. 作为用户，我希望把记忆导出为 Markdown，以便离线检查和备份。
38. 作为用户，我希望 Markdown 不是第二套真源，以便避免双向同步和冲突。
39. 作为维护者，我希望依赖锁定到已验证版本，以便构建和升级可复现。
40. 作为维护者，我希望 Milvus Lite 的 `db_name` 兼容问题在适配器内解决，以便调用方不需要了解底层细节。
41. 作为维护者，我希望 Milvus Lite 的 JSON `in` 和 `not in` 过滤限制在适配器内改写，以便 scope 和生命周期过滤正常工作。
42. 作为维护者，我希望图索引使用 Milvus Lite 持久化，以便重启后不需要重新抽取全部图关系。
43. 作为维护者，我希望安装器检查新依赖，以便全新安装可以直接启动。
44. 作为维护者，我希望旧内核模块和旧测试退场，以便减少重复维护。
45. 作为测试者，我希望使用确定性假模型端点，以便检索和抽取测试可重复。
46. 作为测试者，我希望通过公开守护进程接口验证端到端行为，以便测试不绑定内部实现。
47. 作为测试者，我希望通过存储契约验证 Milvus Lite 适配器，以便覆盖公开接口难以触达的边界。
48. 作为测试者，我希望验证重启后的数据保留，以便确认 SQLite 和 Milvus Lite 的持久化。
49. 作为测试者，我希望验证图扩展和来源引用，以便确认图结果不是无来源事实。
50. 作为测试者，我希望验证后台更正和审计，以便确认用户可以直接治理错误记忆。
51. 作为维护者，我希望不引入长期未更新的 nano-graphrag，以便减少依赖风险和维护成本。
52. 作为用户，我希望为技能或课程建立专题记忆区域，以便学习内容不依赖项目根目录。
53. 作为用户，我希望管理台以记忆区域树展示用户、专题和项目记忆，以便理解记忆的分区。
54. 作为用户，我希望检索接口支持显式跨区域召回，以便后续全局问答能力可以建立在同一数据模型上。
55. 作为用户，我希望在用户记忆和选中的专题或项目记忆之间做跨区域召回，以便智能体可以串联多个区域回答一个问题。
56. 作为用户，我希望全局召回结果按来源区域分组，以便我知道每条事实来自用户记忆、专题记忆还是某个项目。
57. 作为用户，我希望全局召回对用户记忆和每个项目设置预算上限，以便项目事实不会被用户记忆淹没。
58. 作为用户，我希望全局召回必须显式开启，以便项目会话默认不会读取其他项目或用户记忆。
59. 作为用户，我希望选择哪些区域参与全局召回，以便控制检索范围和敏感内容暴露。
60. 作为 Codex 用户，我希望通过 MCP 或命令行开关发起全局召回，以便我可以直接询问跨项目问题。
61. 作为用户，我希望显式记录全局偏好到用户记忆区域，以便它在不同项目中都可用。
62. 作为用户，我希望把课程和技能笔记记录到专题记忆区域，以便学习内容与项目记忆分开。
63. 作为用户，我希望 Codex 的项目采集默认只写入当前项目记忆区域，以便用户记忆不会被项目细节污染。
64. 作为用户，我希望系统自动把稳定的个人事实从项目或专题记忆晋升到用户记忆，以便我不需要手工维护全局记忆。
65. 作为用户，我希望自动晋升要求多个来源或明确陈述作为证据，以便偶然说法不会变成全局事实。
66. 作为用户，我希望自动晋升跳过敏感内容和项目特定内容，以便用户记忆保持干净。
67. 作为用户，我希望晋升后的记忆保留来源项目引用，以便我可以审计它从哪里来。
68. 作为用户，我希望可以更正、降权或遗忘晋升后的记忆，以便错误可以撤销。
69. 作为用户，我希望冲突的项目事实保持未晋升状态，以便系统不会静默选择其中一个。
70. 作为用户，我希望自动晋升在后台运行，以便会话采集保持快速。
71. 作为用户，我希望非项目聊天拥有会话记忆，以便智能体记住当前对话。
72. 作为用户，我希望会话记忆把稳定的个人事实晋升到用户记忆，以便全局偏好可以持续使用。
73. 作为用户，我希望会话或项目记忆把可泛化知识晋升到专题记忆，以便技能和课程知识可以积累。
74. 作为用户，我希望项目特定事实保留在项目记忆，以便用户记忆和专题记忆不被污染。
75. 作为用户，我希望晋升后的记忆显示来源区域和来源单元，以便审计它从哪里来。

## Implementation Decisions

1. `JiuwenMemory 0.2.0` 是唯一记忆内核。写入、存储、索引、检索、生命周期和治理都经 `MemoryAPI` 完成。产品外壳不得保留第二套记忆真源。
2. 保留现有产品外壳：FastAPI 管理台、API Key 鉴权、Codex Hooks、MCP、项目绑定和安装器。外壳只负责接入、绑定、界面和本地生命周期管理。
3. 不做旧版本数据迁移。使用全新状态目录。旧数据、旧图投影和旧状态目录不导入。开发阶段允许清空并重建。
4. Markdown 只作为可选导出视图。不提供旧 Markdown 导入器，不做双向同步，不让 Markdown 成为第二套权威记忆。
5. 记忆区域是逻辑边界。用户记忆区域映射为 `Scope(org="local", space="user", user="<local-user>")`。专题记忆区域映射为 `Scope(org="local", space="topic:<id>", user="<local-user>")`。项目记忆区域映射为 `Scope(org="local", space="project:<id>", user="<local-user>")`，它是绑定项目根目录的专题区域。Codex 采集使用 `agent="codex"` 和会话级 `session`。
6. 项目绑定保存项目根目录到项目记忆区域的显式关联。专题记忆区域不需要项目根目录。worktree 继承主项目绑定必须显式配置。项目绑定不得依赖目录名推断。
7. 会话采集从 Hook 接收用户消息、助手最终回复、会话元数据和任务结果摘要。外壳把事件转换为 mem2.0 的 `add` 请求，并把来源会话、轮次和项目 space 写入来源引用和用户元数据。
8. 取消独立候选审核层。没有独立候选库、候选审批 API 和 `review_state` 过滤。`evolve`、生命周期、`audit`、`inspect`、`update` 和 `delete` 是唯一治理路径。
9. 管理台提供后台更正。`inspect` 读取完整内容和旧版本；`update` 默认使用 `SUPERSEDE` 生成新版本；小范围修正可使用 `OVERWRITE`；`delete` 支持 `FORGET`、`ARCHIVE`、`DOWNWEIGHT` 和 `PURGE`；`audit` 查询留痕；`trace` 沿 `provenance` 追溯来源。
10. 恢复旧内容通过再次 `update` 完成。恢复产生新的版本，不重写历史。
11. 检索经 `MemoryAPI.search` 执行。传入项目 scope 和 `Context`，通过 Context 扩展传入 10K 披露预算，并开启检索轨迹。返回项映射为现有记忆上下文包和 MCP 响应。
12. 检索结果保留内容、来源引用、用户元数据、系统元数据和降级信息。结果不得丢失项目 space、会话来源或生命周期状态。
13. 全文索引和向量索引是两条独立召回通道。全文通道使用 Milvus Lite BM25 和 Jieba 分析器；向量通道使用 Milvus Lite 稠密向量。两者不得互相替代。
14. 图扩展使用项目自有的 Milvus Lite GraphStore 适配器。节点和边分别存入 Milvus Lite collection。`evolve(ASSOCIATE)` 建立记忆单元节点和关系边。图节点使用记忆单元 ID。默认图深度为一跳。遍历在应用层执行。
15. 图扩展是目标功能，不是可选功能。存储 spike 阶段可以先关闭图，spike 通过后必须接入图检索。`nano-graphrag` 最新版停留在 0.0.8.2（2024-10-19），依赖较重，本次不引入。若 Milvus Lite 图适配器无法满足正确性或性能要求，再评估项目自有的其他轻量图存储，但保留图扩展行为。
16. 本地存储组合为 SQLite KV、Milvus Lite 稠密向量、Milvus Lite BM25 全文和 Milvus Lite 图节点/边。开发测试不使用 Docker。SQLite 保存权威记忆单元；Milvus Lite 的向量、全文和图 collection 都是可重建索引。SQLite KV 保留为真源，因为 `KVStore` 需要任意字节值、前缀扫描、批量读取、TTL 和事务性写入；Milvus 不作为键值真源。
17. 项目侧实现 Milvus Lite 的 `FulltextStore` 适配器。适配器只实现存储契约，不承载记忆逻辑。适配器负责 BM25 collection、Jieba 分析器、scope 过滤、元数据过滤、评分方向和重启持久化。
18. Milvus Lite 本地客户端需要显式使用 `db_name="default"`。适配器负责处理该参数，不让调用方感知。
19. Milvus Lite 3.x 不支持对 JSON 字段使用 `in` 和 `not in`。适配器把这两类过滤改写为等值条件的 OR 和 AND 组合。
20. Milvus Lite 适配器需要提供可靠的关闭和释放行为，避免本地 gRPC 服务和数据目录锁残留。
21. 依赖使用最新稳定版。spike 通过后锁定精确版本。初始验证版本为 `JiuwenMemory 0.2.0`、`milvus-lite 3.2.2`、`pymilvus 3.0.2`。不引入 `nano-graphrag`。
22. 安装器检查新依赖、启动守护进程并验证健康检查。安装器不得要求 Docker。旧版本升级兼容不在本次范围内。
23. API Key 仍由产品外壳管理。mem2.0 在进程内使用可信本地安全上下文。记忆内容仍是不可信数据，注入模型上下文时必须保留边界和来源。
24. 保留现有 REST 和 MCP 主契约：健康检查、项目绑定解析、记忆库列表、检索和会话采集。候选相关端点和 MCP 工具退场。新增记忆检视、更正、生命周期和审计端点。
25. 检索失败逐级降级。全文、向量、图或模型故障时返回可用通道的结果，并在响应中报告降级状态。Hook 边界继续 fail-open，不阻塞 Codex。
26. 管理台展示内核健康、索引状态、图状态、记忆单元、版本、生命周期和审计。管理台不维护独立记忆副本。
27. 本地 Git 不再是记忆版本主机制。mem2.0 的版本链、`audit` 和 `supersedes` 是主历史。Git 只作为可选导出备份。
28. 检索上下文包继续执行 10K tokens 硬上限。mem2.0 的披露层级和预算参数可以映射到现有响应，但不得突破上限。
29. 旧自研内核模块退出主路径，包括 Markdown 扫描、分块、混合检索、候选治理、本地 Git 版本和自研图投影。只保留产品外壳需要的适配代码。
30. 新的实现必须保持区域默认隔离。项目会话只检索当前项目 space。跨区域召回必须显式请求，并按来源区域分组。
31. 管理台使用记忆区域树展示用户、专题和项目区域。树是导航和召回策略，不是存储所有权。
32. 跨区域召回的核心能力纳入本 spec：显式选择用户区域和一个或多个专题或项目区域，跨 space 检索，结果按来源区域分组，并受预算上限约束。
33. 全局召回必须显式开启。项目会话默认只检索当前项目 space，不得自动读取其他项目或用户记忆。
34. 全局召回由产品外壳编排。外壳把选中的 region 映射为 mem2.0 space，通过 `Context` 的 spaces 扩展执行跨空间检索，再做来源分组和预算裁剪。
35. 写入记忆时在用户元数据中记录 `region_id` 和 `region_kind`，以便全局召回结果可以稳定标记来源区域。
36. 自动意图判断、共享实体桥、跨用户共享和复杂冲突综合作为后续增强，不阻塞本次核心跨区域召回。
37. 用户记忆区域记录稳定个人信息：偏好、关系、目标、跨项目约束和长期事实。用户记忆的写入路径包括显式管理台操作、显式 MCP 写入，以及证据驱动的自动晋升。项目采集不直接把每条内容写入用户记忆。
38. 专题记忆区域记录技能、课程和领域知识：概念、规则、示例、练习、参考资料和学习进度。专题记忆可以来自显式写入，也可以来自绑定到专题根目录的学习会话。
39. 项目记忆区域记录项目特定事实：决策、约束、架构、缺陷、任务经验和项目内引用。Codex 项目会话的默认采集写入当前项目记忆区域。
40. 普通跨区域召回不复制正文。通用事实写入最宽的有效区域，具体应用写入较窄的区域。自动晋升会创建带 `provenance` 的新单元，源单元保留；这不是无来源的正文复制。
41. 记忆分层建议：用户记忆使用核心、语义和程序记忆；专题记忆使用语义、程序和情景记忆；项目记忆使用情景、语义、程序和归档记忆。工作记忆保持在会话范围，不直接写成全局事实。
42. 写入时在用户元数据中记录 `region_id`、`region_kind`、可选 `topic_id`、可选 `project_id`、来源引用和有效期。管理台用这些字段展示区域、来源和生命周期。
43. 自动晋升是目标能力。用户记忆可以由显式写入和证据驱动的自动晋升共同填充。
44. 晋升目标由分类结果决定：稳定个人事实晋升到用户记忆；可泛化的技能或课程知识晋升到专题记忆；项目特定事实保留在项目记忆。
45. 晋升管线使用 mem2.0 的演进和后台任务能力。流程为候选选择、分类、证据检查、去重、写入目标空间、来源标记和审计。
46. 晋升证据阈值：明确用户陈述且置信度高，或至少两个独立来源重复出现。证据不足时保留原区域，不晋升。
47. 冲突处理：来源之间事实矛盾时跳过自动晋升并记录审计。用户可以在管理台手动解决，不由模型静默选择。
48. 晋升必须幂等。使用规范化内容、目标区域和实体生成晋升键，避免重复创建。重复事实使用去重和 `supersedes` 处理。
49. 晋升必须可撤销。用户可以更正、降权或遗忘晋升后的单元；源单元保留在原区域。
50. 自动晋升在后台执行，放在会话结束或定时任务中，不阻塞采集热路径。敏感内容不得自动晋升。
51. 新增会话记忆区域，使用 `space=chat` 和会话级 `session`。非项目、非专题会话的采集写入该区域，默认保留 30 天，可归档或遗忘。
52. 非项目会话默认召回用户记忆区域和当前会话记忆区域，不召回项目或专题记忆，除非显式选择。
53. 采集路由：项目会话写入项目记忆；绑定专题的学习会话写入专题记忆；无项目、无专题的会话写入会话记忆。
54. 自动晋升不是单向写入用户记忆。晋升来源包括会话、项目和专题记忆；晋升目标是用户记忆或专题记忆；项目特定内容保留在项目记忆；临时内容保留在会话记忆或按保留策略清理。
55. 晋升目标由分类决定：稳定个人事实到用户记忆，可泛化技能或课程知识到匹配的专题记忆，项目特定事实留在项目记忆，无法确定目标时保留原区域。
56. 从会话晋升到项目记忆必须有显式项目绑定或用户操作。系统不得根据会话内容猜测项目归属。
57. 记忆区域树显示用户、专题和项目区域。会话记忆作为用户区域下的当前会话临时节点显示，不作为永久项目子节点。
58. 非项目会话默认召回用户记忆区域和当前会话记忆区域。项目会话默认只查当前项目空间，专题会话默认只查当前专题空间。这个差异必须明确记录，不能被误解为默认跨区域召回。
59. 跨区域召回默认预算：总预算 10K tokens；用户记忆最多 30%；每个选中专题或项目最多 20%；图扩展最多 20%；来源和结构信息最多 10%。预算可配置。
60. 审计使用持久化 SQLite 审计存储，重启后仍可查询。管理台审计页面读取同一存储。
61. 本地守护进程只监听回环地址。产品外壳使用 API Key 鉴权，mem2.0 在进程内使用可信本地安全上下文。不得把本地安全上下文暴露到非回环网络。
62. 管理台提供 Markdown 导出。导出是只读视图，不提供导入，也不构成第二套真源。
63. 保留 REST 和 MCP 的健康、区域绑定、检索和采集主契约。候选相关端点和 MCP 工具退场。新增区域选择、全局召回和记忆治理参数。Codex 插件文档和工具发现同步更新。
64. 状态目录写入版本标记。守护进程不读取旧版本状态目录；重置必须由用户显式触发。
65. 依赖验证覆盖 Python 3.11、3.12 和 3.13。Milvus Lite 3.x 仍是 beta，作为开发测试依赖使用，并在升级前重新验证。
66. 自动晋升测试使用确定性触发或任务状态接口，不依赖实际等待定时任务。

## Testing Decisions

测试只验证外部行为，不验证内部实现细节。测试使用临时目录、确定性假模型端点和真实本地存储。测试数据可以清空。

主测试缝是守护进程公开接口。使用现有 FastAPI 应用装配和 `TestClient` 模式，启动临时状态目录，接入 SQLite KV 和 Milvus Lite，使用确定性假模型端点。覆盖区域注册和绑定、会话采集、`add`、`evolve`、全文检索、向量检索、10K 预算、图扩展、跨区域召回、自动晋升、后台更正、审计、MCP 检索和重启持久化。

跨区域召回测试覆盖默认项目隔离、显式选择多个区域、结果按来源分组、预算上限、用户记忆与项目记忆冲突时保留多个来源，以及未选中的项目不进入结果。

自动晋升测试覆盖：明确陈述和高置信度晋升；多来源重复事实晋升；证据不足不晋升；敏感内容不晋升；项目特定事实不晋升；冲突事实不晋升；会话到用户记忆晋升；会话或项目到专题记忆晋升；项目特定内容留在项目；晋升单元带来源引用；重复运行不产生重复单元；更正和遗忘晋升单元后源单元仍在。

会话记忆测试覆盖：非项目会话写入会话区域；默认召回用户记忆和当前会话记忆；不默认读取项目或专题记忆；保留期后归档或遗忘；从会话晋升后源会话单元仍保留。

存储契约测试缝覆盖 mem2.0 的 `FulltextStore`、`VectorStore` 和 `GraphStore` 适配器。覆盖写入、更新、删除、点查、scope 隔离、元数据过滤、`in` 和 `not in` 改写、BM25 评分方向、Jieba 中文分词、`db_name` 处理、图节点和边 CRUD、BFS、删除级联、关闭释放和重启持久化。该测试缝是新增缝，因为自定义 Milvus Lite 适配器的边界行为无法全部通过公开接口触达。

安装器沿用现有 Linux 安装器和原生安装验证测试。覆盖依赖解析、守护进程启动、健康检查、全新状态目录、状态版本标记和 Python 版本矩阵。安装器测试不引入 Docker。

测试先例包括现有平台接口测试、图记忆测试、敏感治理测试和安装器测试。新测试应复用相同的临时目录、假模型和公开接口风格。自动晋升和跨区域召回在正式 Ticket 前先做 spike，验证 spaces 扩展、来源标记、预算裁剪和跨 space 写入。

验收场景：全新安装启动后绑定一个项目，采集一轮项目会话，检索到相关记忆且不超过 10K tokens。非项目会话写入会话记忆区域，并默认召回用户记忆和当前会话记忆。自动晋升把稳定个人事实写用户记忆，把可泛化知识写专题记忆，项目特定内容留在项目记忆。跨区域召回按来源分组且不超预算。后台更正一条错误记忆并查到审计记录。重启后记忆、图数据和审计仍存在。图扩展返回带来源引用的记忆单元。

## Out of Scope

- 旧版本数据迁移、旧 Markdown 导入和旧状态兼容。
- Markdown 作为权威真源或双向同步。
- 独立候选审核层、候选审批界面和候选状态机。
- 本地 Git 每次变更提交作为记忆版本主机制。
- nano-graphrag 图后端。
- 多用户 RBAC、远程云部署和 Docker 运行时要求。
- 跨区域召回的后续增强：自动意图判断、共享实体桥、跨用户共享和复杂冲突综合。
- 完全无治理的自动晋升：没有证据、审计或撤销路径的自动写入。
- mem2.0 的多模态、群体记忆、Space 权限矩阵等未在本次目标中使用的能力。
- Codex 插件交互方式的重写。只调整必要的接口适配。
- 生产级性能优化、容量规划和发布硬化。

## Further Notes

本规格受 ADR 0021 约束。ADR 0021 记录 mem2.0 替换唯一记忆内核、取消旧数据迁移、取消独立候选审核层、使用轻量本地存储和图检索目标。

已发现的兼容问题必须由适配器处理：Milvus Lite 本地客户端需要 `db_name="default"`；Milvus Lite 3.x 的 JSON `in` 和 `not in` 需要改写；mem2.0 只提供 Milvus `VectorStore`，全文 `FulltextStore` 和图 `GraphStore` 需要项目侧实现。
`nano-graphrag` 最新版停留在 0.0.8.2（2024-10-19），依赖较重，本次不引入。

图接入排在存储 spike 之后。存储 spike 先验证 SQLite KV、Milvus 向量、Milvus BM25、持久化审计、重启持久化和公开接口。spike 通过后接入 Milvus Lite GraphStore。图失败时退回项目自有其他轻量图存储，但不得取消图功能。跨空间召回和自动晋升在正式实现前各做一次 spike。

本项目不做旧数据迁移。开发阶段可以删除状态目录并重新开始。状态目录必须带版本标记，避免误读旧数据。

记忆区域模型：用户区域是展示树的根，专题和项目区域是子区域；存储层是 peer spaces。跨区域召回的核心能力纳入本 spec；自动意图判断、共享实体桥、跨用户共享和复杂冲突综合作为后续增强。

记录规则：用户记忆记录稳定的全局事实和偏好；专题记忆记录技能、课程和领域知识；项目记忆记录项目特定事实；会话记忆记录非项目、非专题会话的临时内容。项目采集默认写入项目区域。用户和专题记忆可以由显式写入和证据驱动的多目标自动晋升共同填充。跨区域召回不复制正文；自动晋升创建带来源引用的新单元，源单元保留。
